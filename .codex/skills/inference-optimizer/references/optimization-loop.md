# Measurement and tuning loop

## Baseline

Before numeric sizing, use [architecture-specific cost models](architecture-cost-models.md) to inventory components, execution phases/frequencies, persistent state, and task metrics. Establish component and end-to-end baselines; apply the text decode profiles below only where relevant. For TTS, benchmark representative text/reference-audio/output-duration profiles and measure first playable audio, chunk deadlines, RTF, and audio seconds/s through the complete generator/vocoder path.

Record the GPU and driver, advertised and available measured bandwidth, SM/compute-unit and tensor resources, clocks/power limits, supported dense compute rates for the actual arithmetic, engine commit/version, model and checkpoint commit, quantization metadata, API flags, measured memory, and dataset. Include image/fork/plugin identity, PyTorch/runtime, and kernel libraries such as FlashAttention, FlashInfer, Triton, and CUTLASS when used. Start with the engine's documented default for the exact model. Confirm a full-context request works before tuning for speed. Keep prompt content and output limits identical across candidates. Read [hardware throughput ceilings](hardware-throughput-ceilings.md) and calculate memory/compute bounds for each feasible quantization and workload before tuning; retain both the theoretical envelope and an independently calibrated estimate. Use capacity to screen fit; speed estimates require actual arithmetic, weight/KV traffic, batching, and layout, including communication for multiple GPUs.

Build at least two workload profiles: (a) one active interactive user and (b) peak requested concurrency. Within each, include realistic short/medium requests and a near-native-window prompt. For repeated-prefix applications, measure both cold and warm prefixes. Report TTFT, inter-token latency or TPOT, end-to-end p50/p95 and p99 with enough samples, output tokens/s per user and aggregate, successful requests/s, error/OOM rate, peak GPU and host memory, and quality. Measure SLO-compliant goodput, queue time, and preemptions/recomputation where exposed; a throughput gain that misses the user's latency target is not a win. Separate prefill and decode bottlenecks. Warm each candidate consistently; include cold-start cost if it matters operationally. Measure sustained clocks, temperature, throttling, and power when a performance limit suggests them. A single short-prompt tokens/s number cannot establish the winner.

## Tuning order

1. **Weights and kernels:** Compare only compatible, quality-acceptable candidates. Check whether the intended optimized quantized-linear, attention, MoE, normalization, and sampling kernels are actually selected in prefill and decode; inspect logs/profiles rather than assuming from checkpoint naming. Note W4A16/weight-only versus W4A4/native FP4 when relevant. Profile excess launches, conversions, and HBM traffic before changing kernels.
2. **Memory and scheduling:** Evaluate [FP8 KV](fp8-kv-cache.md) independently of weights. Tune GPU/KV budget, max sequences, batching limits, and prefill chunking against full context and concurrency. Avoid reservations that cause OOM. For CPU/GPU gaps, inspect tokenization, scheduler work, synchronization, detokenization, and HTTP/client overhead; test supported asynchronous/overlap scheduling. For launch overhead, test CUDA graph modes and capture sizes against actual decode batch shapes, with an eager control; measure capture warmup, graph coverage/fallbacks, and graph buffers competing with KV. Verify compatibility with speculation, structured output, and cache connectors instead of enabling every flag together.
3. **Cache and parallelism:** Measure prefix cache for real prompt overlap. For multi-GPU hardware, run the [sequential TP → PP → DP → EP experiment loop](parallelism-experiments.md), retaining only feasible layouts and applying EP to supported MoE models. Evaluate hybrids and per-GPU fit; more GPUs do not automatically improve single-stream latency. For organizational fleet/Kubernetes workloads, use the [cluster serving comparison](cluster-serving.md) to measure cache-aware routing and prefill/decode disaggregation through the gateway.
4. **Decode acceleration:** Read [speculation and KV offload](speculation-kv-offload.md). Search for exact-model native/attached MTP and compatible draft checkpoints; compare DFlash, EAGLE-style methods, and simple draft-free methods where supported. Track accepted draft tokens, quality, extra memory, and real end-to-end gain. Do not enable a feature solely because a benchmark microcase improves.
5. **Backend comparison:** Run the same workload and API contract on the best plausible second backend. Keep the winner per objective if latency and throughput trade off.

Change one independent variable at a time where possible and preserve the prior best. After each candidate, report measured throughput, fraction of the matching theoretical ceiling and calibrated estimate, and the predicted/profiled limiter; use the unexplained gap to select the next experiment. Follow the [hardware-aware acceptance and stopping rules](hardware-throughput-ceilings.md#compare-measurements-and-decide-when-to-stop): closest to its own ceiling and fastest under the user's requirements can be different winners. Use the engine's current benchmarking CLI, for example [vLLM's serve benchmark](https://docs.vllm.ai/en/latest/benchmarking/cli/) or [SGLang's benchmark tools](https://github.com/sgl-project/sglang/tree/main/benchmark), when it reproduces the intended online workload. An offline or fixed synthetic workload measures that case; it does not predict the user's runtime traffic. Measure through the actual client/API/router, including real arrivals, streaming, tools, cache state, and mixed prefill/decode traffic as applicable, before calling a configuration final.

## Kernel engineering escalation

Profile first. Identify the hot operator, shapes, precision, kernel dispatch, bandwidth/compute utilization, and whether prefill or decode suffers. Check existing upstream issues and recent commits. In a fresh pinned checkout of vLLM, SGLang, or TensorRT-LLM, make the smallest change that addresses the measured bottleneck. Keep the unmodified baseline runnable. Test numerical correctness and model outputs, representative shapes, full context, concurrency, and API contracts; benchmark end-to-end with confidence intervals or repeated runs. Document compiler/driver/GPU constraints and revert if the gain is not real. Do not make or claim model-specific kernel edits without a reproducible profile.

Use a brief Nsight Systems/PyTorch trace to locate gaps, then targeted kernel profiling where needed. Prefer an existing optimized operator/library before authoring a new kernel. Compare custom fused operators against a trusted numerical implementation across relevant shapes; verify model behavior against the model author's implementation when architecture support is new. Disable profiling for the reported performance runs. Sources: [vLLM profiling](https://docs.vllm.ai/en/latest/contributing/profiling/), [vLLM CUDA graphs](https://docs.vllm.ai/en/latest/design/cuda_graphs/), [SGLang tuning](https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning), [FlashInfer kernels](https://docs.flashinfer.ai/).
